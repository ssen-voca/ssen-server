# 교사 계정 잠금 대응과 계정 회수 (이슈 #30)

교사 계정은 학교·이름·번호 4자리로 지켜지고 로그인·가입 시도 제한은 (학교, 이름) 하나(5회/5분)였다. 학생이 선생님의 학교·이름으로 5번 틀리면 선생님이 잠겼고, 설정에서 교사를 빼도 계정이 회수되지 않았다.

## 결정

### 1. 시도 제한을 "계정 + 접속 IP"의 두 겹으로

로그인과 가입(가입도 번호 탐색에 쓰일 수 있어 시도로 센다) 모두 같은 규칙이다.

- **계정+IP 키** `(학교키, 이름키, 접속 IP)`: 기존 한도(`app.auth.max-attempts`, 5회/`attempt-window-millis` 5분). 다른 IP의 실패는 영향이 없다.
- **계정 전체 상한 키** `(학교키, 이름키)`: 더 느슨한 `app.auth.account-max-attempts`(기본 100, 같은 창). 여러 IP로 한 계정에 번호를 대입하는 것을 막는 마지막 방어선이다.
- 선차감이다. 계정+IP 키를 먼저 차감하고(초과면 429, 아무것도 안 셈), 이어서 계정 전체 키를 차감한다(초과면 계정+IP 차감을 되돌리고 429). 거절된 시도는 세지 않는다. 로그인 성공 시 두 키에서 각각 자기 차감 1회를 돌려준다. 응답은 기존과 같은 429 메시지.
- `LoginAttemptLimiter`에 키별 한도를 받는 `tryAcquire(key, maxAttempts)`를 더했다(기존 시그니처·동작 유지).
- 같은 학교 와이파이처럼 여러 학생이 같은 공인 IP를 써도 키에 계정이 들어 있어 서로 영향이 없다.
- IP 단독 제한(IP당 전체 시도)은 만들지 않았다. 프록시 IP 하나에 모두 묶여 서비스 전체가 잠기는 사고를 피하려는 것이다.

### 접속 IP 얻기

`ClientIp`가 구한다. `app.auth.client-ip-header`(환경 변수 `CLIENT_IP_HEADER`, 기본 빈 값)가 비어 있으면 `getRemoteAddr()`. 값이 있으면(예: `X-Forwarded-For`) 그 헤더의 **마지막 값**(쉼표 구분, 공백 제거)을 쓴다. 프록시가 자기가 본 주소를 맨 뒤에 붙이므로 클라이언트가 앞쪽에 넣은 위조 값은 무시된다. 헤더가 없거나 비면 `getRemoteAddr()`로 대체하고, 100자 넘는 값은 자른다.

**안전한 퇴화**: 프록시 뒤에서 IP를 못 구하면(모든 요청이 프록시 IP) 계정+IP 키가 사실상 계정 키가 되어 예전과 같은 동작(5회/5분)이다. 설정을 안 해도 지금보다 나빠지지 않는다. Railway가 실제 접속 IP를 어느 헤더에 싣는지는 **아직 확인하지 못했다**(`docs/deploy.md`의 "접속 IP 확인").

### 2. 교사 번호는 4자리 유지

교사 번호를 길게 하는 변경은 하지 않는다. 서버 설정 형식(`학교|이름|번호4자리`)과 검증은 그대로다. 4자리라 추측하기 쉬우므로 `0000`·`1234`·생일 같은 값을 피하라고 문서에 적는다.

### 3. 교사 계정 회수: 설정이 기준, 목록에서 빼면 비활성

- `app_user.disabled BOOLEAN NOT NULL DEFAULT FALSE`(`V11__teacher_disabled.sql`). `AppUser.disable()`·`enable()`·`isDisabled()`.
- `TeacherAccountSeeder`는 시작할 때 기존 로직(없으면 만들고, 번호가 바뀌면 해시 교체)에 더해 설정에 **있는** 교사가 비활성이면 활성으로 되돌리고, 설정에 **없는** 교사(학교키+이름키, role TEACHER)를 비활성으로 표시한다. **삭제하지 않는다**(수업·단어 데이터 유지).
- **설정이 비어 있으면 아무도 비활성화하지 않고** 경고 로그 한 줄만 남긴다(환경 변수를 실수로 비웠을 때 모든 교사가 막히는 사고 방지). 로그에는 개수만 남기고 이름·학교·번호는 남기지 않는다.
- 적용:
  - 로그인: 비활성 교사는 후보에서 제외해 "없는 계정"과 같은 401(같은 메시지, 같은 BCrypt 비용).
  - 토큰 갱신: 비활성 교사는 401(`InvalidTokenException`).
  - 이미 발급된 액세스 토큰: `TeacherActiveFilter`가 JWT 필터 뒤에서 `ROLE_TEACHER` 요청마다 DB로 활성·존재 여부를 확인하고 아니면 401. 경로 제한은 없고 학생 요청은 DB를 더 조회하지 않는다.
- 가입 충돌 검사 등 기존 학생 흐름은 바꾸지 않는다. 비활성 교사의 번호로 가입하는 것도 계속 409이다(다시 활성이 될 때 학생이 교사와 겹치지 않게).

## 남는 위험

- **번호가 4자리라 추측이 쉽다.** 시도 제한은 늦출 뿐이다. 교사 번호는 피해야 할 값을 문서로만 안내하고 서버가 강제하지 않는다.
- **계정 전체 상한은 분산 대입을 늦출 뿐 막지 못한다.** 한 계정에 5분당 100번(IP 여러 개)까지는 추측할 수 있고, 공격자가 IP를 충분히 가지면 계정 전체 상한이 걸려 교사가 5분간 잠길 수도 있다(잠금 공격은 100배 어려워졌을 뿐 불가능해지지 않았다).
- **같은 IP에서는 여전히 잠글 수 있다.** 같은 학교 와이파이처럼 교사와 같은 IP에서 학생이 교사 이름으로 5번 틀리면 그 IP의 교사는 5분간 잠긴다.
- **IP 헤더 설정이 틀리면 효과가 줄거나 약해진다.** 비워 두거나 잘못 지정하면 예전과 같은 동작이고, 클라이언트가 바꿀 수 있는 헤더를 지정하면 IP별 한도(5회)를 피할 수 있다(계정 전체 상한은 남는다).
- **시도 제한이 메모리 기반이다.** 서버가 1대일 때만 맞고, 재시작하면 초기화된다. IP 키가 늘어 메모리를 더 쓴다(창이 지난 키는 일정 개수를 넘으면 정리한다).
- 회수는 서버를 다시 띄워야 반영된다(시작할 때 맞춘다). 이미 받은 교사 토큰은 다음 요청부터 막히지만, 설정을 바꾸고 재배포하기 전에는 계속 쓸 수 있다.
